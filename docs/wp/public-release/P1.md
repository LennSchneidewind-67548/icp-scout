Planned 2026-10-06, local session (conductor `phase-plan 1`). Feature plan:
[PLAN.md](PLAN.md); its Decisions (V1-V6, N1-N4) are fixed. About 4.5 h of

**Done when:** `python fixtures/demo/make_demo.py` writes a full-size,
clearly fictional `data/example/`. The example demo runs on :8502 with a
populated map and a 50-lead queue, and
`http://localhost:8502/queue?lead=g900000010` opens a lead. `docs/assets/`
holds `pipeline.png`, `demo-queue.png` and `demo-market.png`. `README.md` is
rewritten with the CI badge, the images and a "Run it" section that works

README and case study on the PR branch on GitHub.

## Why P1 looks the way it does

- The committed fixtures give a 34-group market with 3 researched leads, too
  thin for a screenshot. The author picked a synthetic dataset (N1). It is
  built by the real pipeline wherever possible: the three recorded leads go
  through `research.run` in replay mode, and every score comes from
  `score.run` (ADR 0002). Only the inputs that would need the network or a
  model are synthetic.
- Headless Chrome can't click a queue row, and no screenshot tool may be
  added. So a `?lead=` query parameter opens a lead.
- Every image is rendered by the headless Chrome already in the Pipeline
  section, from a source that stays in git. No new dependency, and a wording
  change is one re-render.
- Nothing under `src/` changes in P1. The generator lives in `fixtures/`, the
  deep link in the app file, the rest is docs and images. That keeps the
  tested pipeline exactly as it was presented.
- The texts follow N2: process numbers only (hours, agent sessions, cost per
  researched lead, test count). No market or score numbers from the case run.
  Values from `config/icp.example.yaml` (weights, tier cut-offs, queue size,
  shortlist size) are public config, not run results, so they may appear.

## Step 1: the example dataset (`fixtures/demo/make_demo.py`)

A seeded generator that writes a full-size, clearly fictional `data/`
directory. The existing app reads it unchanged. It reuses
`fixtures/llm/make_fixtures.py`, which imports `tests/conftest.py`, so it
lives in `fixtures/`, not `src/`.

**Interface.** `build(out_dir: Path, n_groups: int = 6000, seed: int = 7) -> None`
and a `main()` with `argparse` (stdlib): `out_dir` positional, default
`data/example`; `--groups`, default 6000. Run as
`python fixtures/demo/make_demo.py [out_dir]`. At the top it inserts
`fixtures/llm` into `sys.path` and imports `make_fixtures`, as
`tests/conftest.py`'s `market_dir` fixture does. Module docstring: what it
writes, that every company is invented, and the run command for the demo
(below).

**Safety.** It writes a marker file `out_dir/.example-data`. If `out_dir`
already holds a `market.parquet` and no marker, it stops with an error and
deletes nothing, so a wrong path can't overwrite the author's case files in
`data/`. With the marker present it clears the directory and writes it again.

**What `build` does, in order:**

1. **The real fixture market.** `make_fixtures.market(out_dir)` writes
   `market.parquet` (34 groups), `companies.parquet` and `funnel.json`.
   Keep the three frames as templates for the synthetic rows.
2. **The three recorded leads.**
   `research.run(icp, out_dir, mode="replay", recordings_dir=ROOT / "fixtures" / "llm",
   group_ids=make_fixtures.GROUPS, log=lambda _: None)` writes
   `research/<group_id>.json` and their `ledger.jsonl` lines, for
   g900000010 (Brise Marine Energies), g900000060 (Vallon Thermique) and
   g900000110 (Cap Horizon Solaire). Their replays then work in the demo.
   `icp` is `config.load(ROOT / "config" / "icp.example.yaml")`.
3. **Synthetic market groups.** `n_groups - 34` rows, each a copy of a real
   `market.parquet` row (`template.to_dict()`) with fields overwritten, so the
   column set matches the real file exactly. Use `random.Random(seed)`
   (stdlib), never the global RNG.
   - `group_id`: `"g0" + f"{i:08d}"`; `members`: one or two SIRENs
     `f"000{n:06d}"`. Real SIRENs never start with 000, so no synthetic
     group can collide with a real company. Most groups have one member,
     about 10% have two.
   - `name` and `member_names`: an invented pseudo-word built from
     syllables (e.g. "Valmorin", "Ternelac") plus a trade word from the
     example config's market ("Thermique", "Solaire", "Énergies", "Climat",
     "Habitat"). Capitals, as the registry spells them. Pseudo-words make a
     clash with a real firm's name unlikely (see Risks).
   - `lat`, `lon`, `region`, `department`: around one of about 40 French city
     centres (a list in the file: name, lat, lon, INSEE region code from
     `insights.REGIONS_FR`, department). Weight the cities roughly by size,
     jitter with `rng.gauss(0, 0.25)` degrees. Mainland and Corsica only.
   - Headcount: draw a band midpoint from a skewed distribution so that about
     600 groups (10%) land inside the segment (30-300 staff). Set
     `headcount_low/mid/high/unknown` to match, then the flags with
     `prefilter.size_flags(mid, unknown, icp.segment.headcount_min,
     icp.segment.headcount_max)`.
   - `product_lines`: from `icp.market.product_lines` keys; about 40% have
     both lines. `domains`: the RGE domains that prove them.
   - `website`: `https://<slug>.example` for about 70%, else `None`.
   - `pre_*` values: `pre_size_fit` from the flags, `pre_product_mix` =
     lines / 2, `pre_growth` 0 or 1, `pre_tech_maturity` = has a website.
     `pre_score` from `prefilter.pre_score(values, icp)`, rounded to 4
     places as `sourcing.group_row` does.
   - `source`: as the template row. Reset `shortlisted` to `False` and
     `exclusion_reason` to `None`; the next step sets them.
4. **The shortlist.** On the synthetic rows only,
   `prefilter.shortlist(rows, size, icp.segment.headcount_max)` with
   `size = icp.prefilter.shortlist_size - 3` (172 at full size), which sets
   `shortlisted` and `exclusion_reason`. On the 34 real rows,
   `shortlisted = group_id in make_fixtures.GROUPS`. Write the combined
   frame to `market.parquet`.
5. **Synthetic research.** For every shortlisted synthetic group, write
   `research/<group_id>.json` in the shape `research.run` writes:
   `{"group_id", "name", "model": icp.research.model, "calls": 1,
   "status": "ok", "reason": None, "flags": [], "result": {"website",
   "signals": {<signal id>: {"value", "found", "rationale_en", "evidence":
   [{"quote", "quote_en", "url"}]}}, "facts": {"product_lines",
   "headcount_stated", "open_roles", "tools_seen"}, "notes_en"}}`.
   - Agent values are 0, 0.5 or 1 (the definitions' scale), drawn with
     probabilities that rise with `pre_score`, so the insight charts look
     plausible without being a straight line. Keep the leads with every
     signal at 1 to about 10, so Brise Marine Energies (all four at 1) lands
     inside the 50-lead queue for the screenshot.
   - Evidence: for each found signal, one or two templated French quotes,
     each with `quote_en` next to it, and a URL on the group's `.example`
     site (`/`, `/recrutement`, `/devis`). Three or four templates per
     signal, filled with the group's headcount, city or a role, for example
     "Une équipe de {n} collaborateurs." / "A team of {n} staff." and
     "Nous recrutons : {role} (CDI, {city})" / "We are hiring: {role_en}
     (permanent, {city})". Every French template in the file has its English
     beside it, and the French has its accents.
   - Then `research.write_signals(icp, out_dir)` builds `signals.parquet`
     from all `research/*.json`, the three recorded leads included.
6. **Regrades.** For every synthetic researched group, write
   `regrade/<group_id>.json`: `{"group_id", "status": "ok", "result":
   {"headcount", "headcount_basis_en", "grades": {"growth": {"value",
   "basis_en"}}, "phrases": {<signal id>: "<at most 8 English words>"}}}`.
   Growth grades use the config's finer scale (0, 0.25, 0.5, 0.75, 1). The
   phrases make `score.reason` read like the real queue. The three recorded
   leads get no regrade, as in the fixtures.
7. **Ledger.** For each synthetic researched group, append one research line
   in the shape `LLM._log` writes (`at`, `lead`, `purpose: "research"`,
   `key`, `model`, token counts, `web_searches`, `web_fetches`, `usd`,
   `replayed: false`). `key` is the SHA-256 of `"synthetic-" + group_id`,
   which has no recording, so the app shows "not recorded" for the replay.
   `usd` is drawn around the mean of the three recorded leads' lines. Then
   rewrite `at` on every line, the replayed ones included, to
   `make_fixtures.CLOCK`, so the "last run" stamp and the screenshots don't
   depend on the day they're generated.
8. **Companies and funnel.** `companies.parquet`: one row per synthetic
   member, copied from a real companies row (`group_id`, `siren`, `name`,
   `band` as an INSEE headcount band code that `sirene.band_mid` reads and
   that fits the group's headcount, `active: True`, the rest from the
   template), appended to the real rows. `funnel.json`: read the fixture run's `funnel.json`, keep its stage
   ids, labels, reasons and order, and replace the counts with ones that are
   consistent with the combined market (`groups` = len(market),
   `active_companies` = active rows in companies, and the `rge_rows`,
   `target_rows` above them). Write it with `funnel.Funnel` (`add`, `write`).
9. **The real scoring and insights.** `score.run(icp, out_dir)`, then
   `insights.run(icp, out_dir)`. No model call, no network, no new recording.
10. Print one line: groups, in segment, researched, queue size, and the run
    command:
    `ICP_SCOUT_CONFIG=config/icp.example.yaml ICP_SCOUT_DATA=data/example ICP_SCOUT_RECORDINGS=fixtures/llm streamlit run app/streamlit_app.py`.
    All three variables are set because `demo.load_env` only fills unset
    `ICP_SCOUT_*` values from `.env`, and the author's `.env` may point at
    `private/`.

**Test (`tests/test_example_data.py`).** A module-scoped fixture runs
`make_demo.build(tmp, n_groups=600)` once. At that size the shortlist is
however many in-segment groups exist, up to 172 synthetic. Tests:

- `demo.load(tmp)` succeeds, and the market has 600 rows with the same
  columns as the real fixture `market.parquet`.
- `insights.run` wrote all six `insights/<finding id>.vl.json` specs
  (`insights.FINDINGS`).
- `demo.replay_steps(fixtures/llm, data.ledger, gid)` is not `None` for each
  of the three `make_fixtures.GROUPS`, and is `None` for a synthetic lead.
- Every evidence URL in `signals.parquet` and every `website` in
  `market.parquet` is `None` or has a host ending in `.example`.
- Every evidence item has a non-empty `quote_en`.
- Two builds with the same seed give equal `scored.parquet` frames
  (`pd.testing.assert_frame_equal`).
- The marker guard: a directory holding a `market.parquet` and no marker
  raises, and the file is still there afterwards.
- At full size (`n_groups=6000`, its own test): 6,000 groups, 175
  researched, 50 rows with a `queue_rank` in `scored.parquet`, and
  g900000010 among them. If this
  test takes more than about 10 s locally, say so in the PR body; don't skip
  it.

## Step 7: the case study (`docs/case-study.md`)

A public write-up for someone who never saw the case (V5): first person,
past tense, plain and short in the build log's tone, about 1,200 words
(`wc -w`, 1,000-1,400 is fine), each lesson as a bold lead-in. Process
numbers only (N2). The case company is never named; the framing is "a
take-home case for a GTM engineering role".

Sections:

- **The problem.** The brief in general terms, as `docs/requirements.md`
  states it: source 50 target companies for a B2B software vendor in one
  country and segment, score each 1-10 with explained logic, present the
  patterns, sketch a scalable outbound process.
- **The approach.** The whole market from open data, then the agent on a
  shortlist, then the rubric, then the hand-off. Link the ADRs and the
  pipeline image.
- **What I learned.** Draft each candidate lesson below as a bold lead-in
  plus a short paragraph. Each comes from a committed doc; the source is in
  brackets. The author cuts or reorders in review.
  - Start from the whole market, not a list. Completeness turns the list
    into market insight, and agent money goes only to a shortlist (ADR 0001).
  - Let the model extract and the rubric score. Evidence makes a score
    checkable, and weights become a business conversation that re-ranks live
    (ADR 0002).
  - Real company structure matters: rolling sister companies up to groups
    changed who qualifies on size (`docs/wp/wp1-sourcing.md`).
  - Small firms have a thin web presence, so research cost is driven by
    search and fetches more than by the model (`docs/wp/wp2-research.md`,
    build log WP0/WP2 entries).
  - A rubric saturates: when the top leads max every signal, weights can't
    separate them. Finer grades applied to the recorded evidence fix the cut
    without new research (`docs/wp/wp3-scoring.md`, the WP5 finding in
    `docs/wp/wp5-demo.md`). Say it without the case's counts.
  - Record every model answer: the demo runs offline, CI needs no key,
    re-scoring is free, and the replay shows the agent's work (WP2, WP5).
  - Building with an agent: what it caught and what the author caught, two
    or three examples from the build log's "caught" lines.
- **What I'd do next.** The n8n workflow (out of scope in
  `docs/requirements.md`), CRM sync beyond the CSV import, triggers that

## Risks

- **A synthetic name matches a real firm.** A screenshot would then show a
  real company with a made-up score. Pseudo-word names, SIRENs starting with
  000, `.example` URLs everywhere, and captions that say "synthetic data,
  fictional companies". The three recorded leads' names are the existing
  fixtures', already public in git.
- **`.env` pulls the case data into a screenshot.** All three `ICP_SCOUT_*`
  variables are set on the command line, and step 4's check looks for the
  example vendor in the top bar.
- **The replay of the recorded leads misses** if the prompt or config
  changed since `fixtures/llm/` was recorded. `research.run` in replay mode
  then raises `RecordingMiss`. The existing research tests replay the same
  recordings, so a green `pytest` rules this out. If it happens anyway, stop
  and report; don't re-record in P1.
- **The full-size test is slow** (6,000 rows, then the insight charts). It
  stays, and the PR body says how long it took.
- **Headless Chrome screenshots before the charts draw.**
  `--virtual-time-budget=10000` gives Streamlit and Vega time; if the map is
  still blank, raise it to 20000 before changing anything else.
- **Case-run numbers already sit in committed docs** (the WP plans and the
  build log). They stay (PLAN: the WP plans are the historical record). N2
  binds only the new public texts.
